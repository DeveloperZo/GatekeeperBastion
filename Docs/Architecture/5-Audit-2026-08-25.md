Scope: `Assets/Scripts` (Sim/, Game/, Editor/), `main`, clean working tree. Checks specific
rules already written down in AGENTS.md §4 and gkb-development, not a general quality pass —
this audit does not re-run the SRP/naming/KISS lenses `5-Audit-2026-08-10.md` used.

**Headline: the two rules with the clearest bright line — the Sim/ seam and fake-null hygiene
— hold almost perfectly. The failures are in the rules that depend on habit rather than a
compile-time boundary**: a tracked scratch folder that was never emptied, three HUD prompt
getters that allocate every frame, and a serialized-defaults convention followed in five files
and skipped in the rest of the tunable MonoBehaviour set.

## Clean

Checked by this pass and not present:

- **The Sim/ seam holds but for one field** (below). No `MonoBehaviour`, `GameObject`, scene
  lookup, `UnityEngine.Time`, or ambient `UnityEngine.Random` in any of the 70 files under
  `Assets/Scripts/Sim/`.
- **Fake-null hygiene holds outside Sim/.** 18 raw `?.`/`??`/`??=`/`is null` hits across 212
  non-Sim files; every one resolves to a plain C# type (string, or a value returned from a
  method that returns real `null`), none to a `UnityEngine.Object`-derived operand.
- **No `GUILayout` in the Bastion HUD.** `HudController`, `ShipHud`, `DevConsole` and
  `DevTaintBanner` all use immediate-mode `GUI.*` calls only; two of them carry comments
  naming the layout-stack-fault risk explicitly.
- **No milestone ID in any identifier.** Zero hits for `M\d+` in a class, file, namespace or
  `[MenuItem(` name anywhere under `Assets/Scripts/`.
- **`partial` class discipline holds project-wide.** Every multi-file partial checked
  (`GameController`, `RunSim`, `PlayerGun`, `NetPlayerAvatar`, `HudController`,
  `EnemyGatekeeper`, `WaveSpawner`, `BastionSegment`, `DevConsole`, `SceneBuilder`, others)
  pairs its split with a stated, cohesive concern per file — including the ones plainly
  triggered by the line cap.
- **No LINQ, no closures, and no per-frame array-property reads anywhere in the codebase.**
  `using System.Linq` does not appear once.

## Findings

1. **`MasterControl.HatchWaves` is static mutable state inside `Sim/`.**
   `Assets/Scripts/Sim/Run/MasterControl.cs:13` — `public static int HatchWaves = 1;`. The
   class's own comment documents that tests write and restore it; the boundary rule's
   exception is `static readonly` constants, not a mutable field tests are trusted to reset.
   This is also the same open question `5-Audit-2026-08-10` and the M96 session both flagged
   from a different angle (whether `HatchWaves` should retire to a `const` now it is 1) —
   three independent findings on the same field.

2. **`Assets/_Scratch/` was never emptied.** Convention (gkb-development, "one-shot editor
   work") is `.gitkeep` only between sessions. Tracked instead: `PostProcessingSetup.cs`,
   `ReflectionProbeSetup.cs`, `ExploreFlyCamera.cs`, `ExplorePanel.cs`,
   `ExplorePanelPreset.cs`, `Editor/ExploreRoomBuilder.cs`, `Editor/ExploreComposerWindow.cs`,
   `Editor/RunProtocolBarBuild.cs`, `Editor/ExplorePanelEditor.cs`, and a `Generated/` tree of
   kit walls/panels/materials and two `.asset` files. No `[InitializeOnLoad]` self-delete
   pattern found — these were left by hand, not a broken cleanup mechanism.

3. **Three HUD `Prompt` getters allocate every frame the interactable is in view**, reached via
   `Interactor.Update() → Tick() → _current.Prompt`:
   - `Assets/Scripts/Game/Bastion/RepairInteractable.cs:121,122,130,134,140-141,143,146` — raw
     `$"..."` interpolation in several branches, despite the file already caching a
     `StringBuilder` for one other branch.
   - `Assets/Scripts/Game/Ship/StationTerminal.cs:51-53` — string concatenation, base class for
     all four Ship stations.
   - `Assets/Scripts/Game/Bastion/BastionTerminal.cs:115,117,130,134,136,148` — string
     concatenation in the terminal-complete/wave-live/wave-pending/blocked branches, while the
     Master/Field-armed branches in the same file already use the cached `StringBuilder`.

4. **Serialized-defaults-outrank-code-defaults is the exception, not the rule.** Only 5
   MonoBehaviours project-wide implement `Reset()` for their tunables
   (`CloakerGatekeeper.cs`, `BastionTerminal.cs`, `SpawnRoom.cs`, `RunSeats.cs`,
   `WallRenderState.cs`). Sampled against the highest-value tunable classes, none of these
   have one: `EnemyGatekeeper.cs` (10 combat tunables — damage, aggro/notice radii, chase
   speed, lines 41-69), `PlayerGun.cs` (6 weapon tunables, lines 32-37), `Damageable.cs`
   (`maxHp`, `hitFlashSeconds`), `FirstPersonController.cs` (5 movement tunables). Notably
   `CloakerGatekeeper`, a subclass of the non-compliant `EnemyGatekeeper`, implements `Reset()`
   correctly for its own two added fields — the convention is known one level down and absent
   on the base class carrying most of the combat numbers.

## Decision needed — Zo's, not schedulable by an agent

- **`RealmShareBeacon` is a static-instance MonoBehaviour outside the allow-list.**
  `Assets/Scripts/Game/Flow/RealmShareBeacon.cs:18` — lazy-created, `DontDestroyOnLoad`'d,
  guarded by `Ensure()`/`Retire()`. `Docs/Architecture/README.md`'s allow-list names
  `HatchStation` only. Milder shape than a service locator (internal-only, nothing reads
  state through it externally), so this may be a grandfather-and-document call rather than a
  refactor — but it isn't on the fence today, and the next `lint-arch` pass that checks for
  this would need to know which way it's ruled.
